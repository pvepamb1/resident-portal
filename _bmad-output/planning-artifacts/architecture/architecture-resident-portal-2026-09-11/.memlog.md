- (decision) [ADOPTED] AD-5 (new) -- Identity resolution across auth methods. Binds: CAP-6, CAP-7. Prevents: the same real person ending up with two disconnected accounts after using a different sign-in method than before -- Better Auth's native cross-provider account linking is documented as unreliable (creates a second account by default unless told explicitly). Rule: every sign-in method (Google OAuth, phone+OTP, email magic link) authenticates via the Auth port purely to prove control of one identifier. A separate application-owned resolution step matches that identifier against the landlord-recorded phone/email on the tenant record (CAP-6) or the single allowlisted identifier (CAP-7, no ambiguity -- one identity only). An identifier that doesn't match anything on file triggers one-time confirmation of an already-on-file identifier before linking -- never silently creates a second account for an existing tenant. No password-based method exists anywhere in this system (SPEC.md non-goal).
- (decision) [ADOPTED] AD-6 (new) -- Tenancy-end revocation and export. Binds: CAP-8. Prevents: a former tenant retaining live access via an already-issued session/token after their tenancy ends, because 'revoke access' was implemented as only blocking new logins rather than invalidating existing sessions -- a common real bug with JWT/session-based auth that doesn't auto-revoke on a disabled flag. Rule: ending a tenancy immediately invalidates all of that tenant's active sessions (explicit session revocation, checked on every request, not just at login) and, in the same operation, generates a point-in-time export of their payment history for that tenancy, stored via the same object-storage-behind-signed-URL pattern AD-4 already uses for lease documents, delivered via the Notifier port (see Structural Seed). No ongoing login is ever granted to an ended tenancy -- only the one-time export.
- (decision) AD-2 EXTENDED (Binds now includes CAP-9): a refund webhook can be redelivered exactly like a payment webhook -- same idempotent-dedup rule applies, not a separate mechanism. Refund amount is also bound by SPEC.md's constraint that it can never exceed the amount originally paid -- enforced as part of the same money-correctness discipline, checked before the refund API call is made, not just recorded after the fact.
- (decision) AD-2 EXTENDED further: reminder suppression logic corrected to match SPEC.md's fix -- a reminder is suppressed only when THIS CYCLE's Autopay auto-debit has actually succeeded, never merely because a mandate exists.
