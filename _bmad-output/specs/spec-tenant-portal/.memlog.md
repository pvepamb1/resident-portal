- (capability) CAP-1 intent: landlord and tenant can move real rent money through the app via a licensed payment gateway, not just record it. success: a real UPI transaction completes end-to-end through the gateway and appears in payment history.
- (capability) CAP-2 intent: tenant receives rent-due reminders and can pay via a one-tap link with no app install or account enrollment. success: a reminder is sent and the linked payment completes without any prior signup step.
- (capability) CAP-3 intent: landlord can see a running payment history per tenant/unit. success: history reflects every completed transaction accurately, matching the gateway's settlement record.
- (capability) CAP-4 intent: landlord and tenant can store and view lease documents in-app with no tenant enrollment required. success: a document the landlord uploads is viewable by the tenant through the same no-install link flow.
- (capability) CAP-5 intent: tenant can set up a recurring UPI Autopay mandate so rent auto-debits monthly without manual action each cycle. success: a mandate created once continues to auto-debit on schedule, with tap-to-confirm handled inside the tenant's own UPI app via NPCI push.
- (constraint) App is pure orchestration on a licensed payment gateway (Razorpay/Cashfree-class) and never custodies funds -- keeps it out of RBI Payment Aggregator licensing.
- (constraint) POC built for single-landlord (Prasenna's own) use first; payment module must stay isolated/modular so productizing later means rewriting that layer only, not the app.
- (constraint) Design for 1-5 unit landlords; do not optimize for large multi-unit portfolios or property managers.
- (constraint) Auto-pay's tap-to-confirm step must happen inside the tenant's own UPI app via NPCI push -- a website is sufficient, no native mobile app required.
- (constraint) Verify the current UPI Autopay AFA (additional factor authentication) threshold and mandate rules against the chosen gateway's actual docs before implementing CAP-5 -- not yet confirmed, only recalled.
- (constraint) If a paid tier ever launches, whoever is already using the product at that point stays free -- no retroactive paywalling of existing users.
- (decision) Non-goal: gated-community/society management -- different problem, different buyer, explicitly ruled out.
- (decision) Non-goal: large multi-unit portfolios/property managers as primary target -- demoted to an explicit stretch goal; a separate app gets built later if scaling ever demands it, this spec is not designed for that case.
- (decision) Non-goal: TDS (Sec 194-IB) calculation/withholding handling in this build -- deferred post-MVP as a future capability, not part of this spec's scope.
- (decision) Non-goal: auto-filing Form 26QC or issuing Form 16C on the tenant's behalf -- downgraded to a backlog research question (feasibility unverified, and the beneficiary is the tenant, not the paying landlord), not something this build does.
- (decision) Non-goal: deciding or building a monetization/paid-tier model now -- deferred by design; only the free-tier grandfather guardrail is locked (see Constraints).
